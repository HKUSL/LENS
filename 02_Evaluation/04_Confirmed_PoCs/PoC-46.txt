### **Threat Model:**
- **Attack Assumption:**
  - The victim is the **HSS** on the **Cx** interface. Due to exposure/misconfiguration, an Internet attacker can impersonate an expected **S-CSCF** and send a forged **Server-Assignment-Request (SAR)** directly to the HSS, which accepts it as a valid Cx request.

- **Attacker Capability:**
  - The attacker can open its own Diameter connection to the HSS, send arbitrary SAR requests, and receive the corresponding SAA answers. The attacker does not observe or alter legitimate Diameter links and has no extra SIP/IMS data-plane control unless independently implied by the forged values. The attacker knows the target subscriber identity needed in `User-Name` and, where needed, `Public-Identity`.

### **Exploitability Analysis:**
`Server-Assignment-Type` is a **top-level, vendor-specific 3GPP Enumerated AVP** in `Server-Assignment-Request`, and it is functionally mandatory because it tells the HSS which server-assignment operation to perform. This is not descriptive metadata: the HSS uses it as **authoritative control input** to choose among materially different registration-state transitions.

The field is therefore **field-specifically exploitable** under the stated threat model. If the attacker sends a forged SAR with a malicious `Server-Assignment-Type`, the HSS will branch into different processing paths for the targeted IMS subscriber. In particular, choosing a de-registration, timeout-removal, or administrative-removal style value can cause the HSS to clear or invalidate the subscriber's stored S-CSCF binding and IMS registration state; choosing a registration or re-registration style value can create or refresh a binding to the attacker-chosen `Server-Name`; and choosing a profile-restoration style value can induce profile delivery behavior. The incremental harm comes from **which action the HSS takes**, and that is selected by this AVP.

The causal chain is direct: **forged SAR accepted by HSS -> HSS reads `Server-Assignment-Type` -> HSS updates subscriber IMS registration/assignment state accordingly -> later IMS control-plane behavior consumes that poisoned state -> subscriber-visible IMS disruption or misbinding occurs**. A malicious de-registration-type value yields a concrete service-denial outcome even without any additional attacker-controlled IMS infrastructure, because the HSS itself removes or invalidates the serving assignment. That makes the field independently security-relevant, not merely incidental to the SAR procedure.

There is an attacker-realizability limit for interception-style outcomes: if the attacker sets a registration-style assignment toward an attacker-chosen `Server-Name` but does not actually control that S-CSCF or routing path, full service takeover may not be realizable. However, this does **not** defeat exploitability overall, because de-registration/removal values still create concrete field-driven harm entirely within the HSS's own stored state. The poisoned state is persistent until overwritten by later legitimate re-registration, timeout handling, administrative cleanup, or another valid assignment event.

### **Attack Procedure:**
Craft a forged **Cx Server-Assignment-Request** from the attacker-controlled Diameter connection to the HSS, including the minimal mandatory AVPs: `Session-Id`, `Vendor-Specific-Application-Id` (with Vendor-Id `10415` and Cx/Dx application id), `Auth-Session-State`, `Origin-Host`, `Origin-Realm`, `Destination-Realm`, typically `Destination-Host`, `User-Name`, `Server-Name`, and the target `Server-Assignment-Type`. Include `Public-Identity` where needed for coherent subscriber selection.

Set `Server-Assignment-Type` to a **de-registration / timeout / administrative-removal** style enumerated value supported by the target release. The expected success condition is that the HSS returns a successful SAA and thereafter the targeted subscriber's IMS registration/binding state is cleared or altered, causing loss of IMS registration continuity or service until legitimate re-registration restores state.
